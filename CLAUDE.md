# sabalive (Flutter consumer app + Supabase backend)

Social live-streaming, audio rooms, PK battles, gifting. Flutter (Dart ^3.11) + Supabase
+ Agora RTC. Also owns the whole database and all Edge Functions.

## Commands
```bash
flutter pub get
flutter analyze        # ~12 pre-existing infos; don't add new ones
flutter test           # keep green
flutter build appbundle   # Play; bump version in pubspec.yaml (+N) per upload
supabase db push       # apply migrations (linked to the project) - LIVE: read docs/DEPLOY_CHECKLIST.md first
supabase functions deploy <name>
scripts/db/replay_migrations.sh      # replay every migration on a throwaway local Postgres
scripts/prod/healthcheck.sh          # read-only: is production healthy?
scripts/prod/smoke_play_app.sh       # replays the Play app's key actions, rolled back
scripts/prod/backup.sh               # data + schema backup to ~/sabalive-backups (before every push)
```
Production is shared with the live Play app: follow "Production safety" in the root CLAUDE.md.

## Layout
- `lib/features/*` screens (live/ has watch_live, watch_audio_room, watch_pk_battle,
  and the host screens), `lib/data/*` repositories, `lib/state/*` controllers
  (provider), `lib/services/*` (agora, permissions, push), `lib/config/*`.
- `supabase/migrations`, `supabase/functions` (agora-token, invite-staff,
  ghost-admin, admin-update-staff-auth, send-push, request-account-deletion).

## Conventions and gotchas
- Presence is table-based, not Agora/Supabase presence: `live_stream_viewers`,
  `join_live_stream`/`leave_live_stream`/`heartbeat_viewer`. Viewers join Agora as
  audience (never announced to others). Channel name = `live_streams.id`.
- Ban/block checks go through `live_access_denied_reason` (SQL) so app, triggers and
  `agora-token` agree.
- Android permissions: no READ_MEDIA_*/storage (Play policy). Photos use
  image_picker's system Photo Picker (`avatar_picker.dart`). Don't re-add them.
- Staff accounts are signed out by `StaffAccountGate`; ghost accounts are normal
  users with `AppUser.isGhost`, and the watch screens hide chat/gift/like/follow/seat
  controls for them (`isGhostViewer`). The server enforces view-only regardless.
- Tests: `test/` is broad; add one next to any logic you change.

## Live room internals (easy to break)
- The live screen is mounted in an overlay Navigator (`ActiveLiveSessionController.navKey`); its
  OverlayEntry must keep `maintainState: true` or anything opened over it tears the live down.
- Open pages from inside a live with `AppNav.open/_push` -> `OverLiveRoute` (sheet); never push a
  MaterialPageRoute directly there.
- System back goes through `_LiveBackInterceptor` -> `ActiveLiveSessionController.handleBack`
  (screens register `backHandler`); don't add `didPopRoute` to live screens.
- `LiveBackGuard` (wraps `_RootGate`) blocks pop on the home route while a full-screen live is up. Without it
  Android 16 (targetSdk 36) lets the system take the back gesture and the user is thrown out of the live
  instead of seeing "leave / end?". Keep it, and keep the live out of the root Navigator's routes.
- Heat / battery: avatar frames animate only at `size >= kAnimatedFrameMinSize`; Realtime bursts on lists are
  coalesced with `CoalescedRunner`; the host clock is a `ValueNotifier` (never `setState` on the whole screen
  from a timer). Don't add looping animations or `ImageFilter.blur` to anything shown during a live
  (the speaking waves are the exception: they run only while someone is talking). Don't mute remote video
  or audio when the app is backgrounded: the product wants the live's audio to keep going.
- Cost control (Supabase meters are multiplied by phones): `live_streams` changes on every heartbeat, join, leave, like and gift and Realtime sends each change to EVERY listener, so
  `LiveStreamsController` reloads at most once per 8 s (`ThrottledRunner`; `CoalescedRunner` still has a 1.5 s window, too short for a table that never stops changing), listens only
  while the app is in the foreground and no live is open full-screen (`setInLiveRoom`), and avatars / card photos are decoded at the size drawn (`ResizeImage`) and kept on the phone after the first download (`DiskCachedNetworkImage`, never plain `NetworkImage` / `Image.network` for user or catalogue pictures). Never subscribe to a
  whole table without a filter in a screen, never poll faster than 20 s without a reason, and prefer one shared timer to one per screen. See `docs/OPTIMIZATION_AND_SUPABASE_2026-10-23.md`.

## MS cloud (hosted LiveKit server) next to Agora (owner, 2026-11-06: "bring the app also on MS cloud"; BUILT ON STAGING, not tested on phones by me, not on production, nothing committed)
A live room is carried by ONE provider for its whole life: `live_streams.rtc_provider` = `'agora'` (default, every older room) or `'livekit'` (migration `20261106130000_rtc_provider`, additive, rollback `supabase/rollbacks/20261106130000_down.sql`).
The host's build chooses it when the room is created (`LiveStreamsController.createStream`, `RtcConfig.forNewLives` from `--dart-define=RTC_PROVIDER=livekit`; the column is only sent when it is not agora, so an Agora room is created exactly as before on any database) and every viewer's app reads it (`LiveStream.rtcProvider`, `onLiveKit`) to join the right server.
- **Which builds:** `scripts/staging/build_apk.sh` and `scripts/staging/run_app.sh` set `RTC_PROVIDER=livekit` (`STAGING_RTC_PROVIDER=agora` keeps Agora). A PLAY build does not fix the provider (`AppEnvironment.validate` and `build_play_bundle.sh` refuse `RTC_PROVIDER` at build time); the lives it starts follow the SERVER SWITCH `rtc_livekit_new_lives` (`RtcConfig.serverSwitch`, panel -> Application Config -> Release controls -> "MS cloud for new lives", Super Admin, default OFF = Agora; `RtcConfig.forNewLives` reads it at the moment a live is created). Flipping it never moves a live that is already running (a live is on one provider for life). Turn it on ONLY after the `livekit-token` secrets are set on the project and the minimum Android version code has been raised past every build that cannot join an MS cloud room. A host who picks the PK tab in Go Live always gets an Agora room (PK battles move people between Agora channels).
- **The adapter:** `lib/services/livekit_session.dart` (`LiveKitSession`, package `livekit_client`, which ships WebRTC `libjingle_peerconnection_so.so`, +12 MB per ABI; it builds next to `agora_rtc_engine` with no native clash). Token from the Edge Function `livekit-token` (identity = Supabase user id; host may publish, a seat holder may with a 10-minute token, a viewer may not, a ghost is hidden and view-only; same bans / access checks as `agora-token`). **The trick that keeps the screens unchanged:** the live screens map voices to seats and detect leavers by an Agora-style uid, so every person on MS cloud gets a stable non-zero 32-bit uid worked out from their account id (`liveKitUidOf`, FNV-1a over the lower-cased id: the VALUES ARE STORED in `live_stream_seats.agora_uid` / `live_streams.host_agora_uid`, so the algorithm must never change; reference values are in `test/rtc_provider_test.dart`) and the adapter reports volume as `AudioVolumeInfo` (this phone = uid 0), joins and leaves as uids. The screens extracted their Agora handler bodies into `_onVolume` / `_onRemoteJoined` / `_onRemoteOffline` (called by both servers), and `_switchRtcRole` / `_muteMyMic` choose the server. A seat's uid is bound from the occupant's id (`_bindLiveKitSeats`), not waited for from the row.
- **Role changes** (a viewer takes a seat, a seat holder loses it) reconnect with a new token (MS cloud decides publishing by the TOKEN; a blink of a second or two). The server refreshes tokens itself; a seat holder's 10-minute token is renewed that way (to be confirmed on a long session).
- **Covered:** audio rooms (listen, seats, speaking rings, mute, leave) and video lives (host camera + mic, viewers see the host, guests on seats speak). **NOT covered, Agora-only:** PK battles, the local music mixer, the beauty filter, the funny voice (each says "not available in this live yet" in an MS cloud live), 1:1 calls, and the panel's Live Monitor (it watches with the Agora web SDK, so it cannot watch an MS cloud room; Kill stream still works). Audio is routed as MEDIA volume (`AudioSessionOptions.mediaPlayback`), like the Agora game-streaming scenario; if voices come out quiet or echo on a real phone, that is the first thing to look at.
- **Server fact found on 2026-11-06:** the LiveCore server rejects `canPublishSources` spelled as text (`"microphone"`: 500 "Cannot convert TrackSource microphone to string") and accepts the TrackSource NUMBER (`[2]`); the token function sends numbers (`grants.ts`). `scripts/staging/verify_livekit_rooms.sh` (real requests as the fake host and a fake user, then the MS cloud server's `/rtc/validate` on each token) is the check that caught it.
- **Before any production use:** old apps would still LIST a livekit room and fail to join it, so they must be kept from seeing those rooms first (like `pk_ready` for PK); the production project needs the migration, the `livekit-token` function and its three secrets; an iOS build was NOT tried (Podfile / WebRTC pod, 16 KB page size and APK size checks are open). Tests: `test/rtc_provider_test.dart`, `scripts/db/tests/rtc_provider_test.sql`, `supabase/functions/livekit-token/livekit_jwt.test.ts`.

## PK battles (a layer over audio lives; HANDOFF.md has the plan and the status)

  (`lib/state/`) follows one live's rows through `PkBattlesApi` (the real `PkBattlesRepository`, or a fake in tests), runs the 3 s
  countdown and a timer against the SERVER clock (`pk_now()`), and never decides a score, a winner or a length.

## Undoing a test account's gifts (2026-11-02, `scripts/prod/revert_user_gifts.sh`)
One-off data tool in the style of `follow_everyone.sh`: `scripts/prod/revert_user_gifts.sh <User ID> --from "<UTC>" --to "<UTC>"` is the PLAN (read-only); `--apply` undoes every gift the person SENT or RECEIVED in that window so the database looks as if it was never sent
(sender gets the coins back, receiver loses the diamonds, the `gift_transactions` row and its two `wallet_ledger` rows are deleted, so rankings, Salary and the diamond reset forget it; `xp` / `wealth_xp` / `charm_xp` and their levels go down by the same amount; `live_streams.gift_coin_total` too);
`--undo <pack file>` puts exactly that back (the apply saves a private pack, `~/sabalive-backups/gift-revert-<id>-<stamp>.json`). The ledger rows are not linked to the gift row by id, so they are matched by person + amount + time (a gift and its two ledger rows share `created_at`);
anything that does not match, a receiver who no longer holds the diamonds, or XP that would go below 0 is a BLOCKER and the apply changes nothing. Production needs a backup under 6 h old, a clean healthcheck, a plan without blockers and the User ID typed (or `REVERT_CONFIRM=<id>`), and the owner's go.
`scripts/db/tests/revert_user_gifts_test.sql` proves it with the real `send_gift_v2`: after the apply EVERY wallet, xp, level, gift, ledger row, live total, ranking and stream diamond equals the state before the gifts; the undo restores the state after them (20 checks).
An admin pull-back (`grant_reversal`) is NOT a gift: a receiver whose diamonds were pulled back earlier is a blocker, which is why old gifts (29-31 Oct to 17 accounts) could not be undone and only the 1 Nov burst could.

## Crash and freeze reports (Firebase Crashlytics, Android only)
- `lib/services/crash_reporting.dart`, started in `main.dart` right after `Firebase.initializeApp()`. Needs `firebase_crashlytics` (Flutter) +
  the Gradle plugin `com.google.firebase.crashlytics` + `firebase-crashlytics-ndk` (native crashes: the Flutter plugin only brings the Java side).
  The owner must open the Firebase console -> Crashlytics once (Enable) before reports show. A report carries: the stack (Java, native, Dart),
  the last `CrashReporting.log` lines (live opened / left, Agora connection states, gift sheet and gift sends), a memory line every 30 s (app MB,
  decoded gift animations MB, picture cache MB) and the signed-in person's VISIBLE app ID (`display_id`, never for a ghost; no name, email or phone).
- `reportPreviousExits()` asks Android (`ApplicationExitInfo`, MainActivity.kt channel `com.sabalive.in/exit_info`, Android 11+) why the last
  process ended and sends the ones that matter once each (`PreviousExits.toReport`): a kill for memory / a freeze / a native crash leaves no crash
  otherwise. Android 10 and older send nothing.
- iPhone sends NOTHING: `FirebaseCrashlyticsCollectionEnabled = false` in `ios/Runner/Info.plist` and the start-up refuses non-Android. Before it is
  turned on for iOS: the App Store privacy label, dSYM upload, and the Play Data safety form needs "Crash logs" (+ "User IDs") before ANY Play release
  of a build that has this. Native frames show library names and addresses (no symbol upload is set up).
- Dart errors are sent as NON-fatal (a release build does not close on them); fatal = the process really died. Debug builds send nothing.

## Bans (device / account / identity / IP)
- An account or device ban (`user_bans`) also writes to `banned_identities` (normalized email / phone / Google / Apple id; gmail
  dots, `+tag` and `googlemail` are folded) and `banned_ips` (24 h, new accounts only, skipped for IPs seen with 4+ accounts). These
  outlive the account (`user_bans.user_id` is `on delete set null`), and a lift releases them (`release_ban_signals`).
- Enforcement: BEFORE INSERT triggers on `auth.users` / `auth.identities` refuse a banned identity with SQLSTATE `BN010` for
  ANY client, old or modified. They fail open on internal errors: a bug must never stop honest sign-ups. Keep them that way.
- The app calls `check_signup_access` (anon-callable) before sign-in / sign-up with every device id and falls back to
  `check_device_access` on an older server. `register_device_v2` stores a second Android id (`drm:` Widevine hardware id, survives a
  factory reset) and spreads a ban to all of a user's ids. The Kotlin `device_ids` channel is a thin wrapper: no id = no extra id.
- The sign-up IP is only visible to the `before_user_created_hook` Auth hook (Dashboard -> Authentication -> Hooks), which is
  inert until the owner enables it. MAC addresses are unreadable on modern Android / iOS: never promise a MAC ban.
- Retiring old app versions = the minimum Android version code in Master -> Config -> Release controls (owner's release decision).
- Staff see "Linked accounts" on a user's profile (`admin_linked_accounts`: same phone / network / login).
- Ban length and reason (2026-10-25, migration `20261025120000`): `ban_user_v2(user, kinds, duration, reason, ends_at)` adds `24h` and `custom` (an end date 5 minutes to 10 years ahead) to `7d` / `30d` /
  `permanent`; presets are worked out on the SERVER clock. `ban_user` stays (`set_profile_status` calls it). A reason typed through v2 is marked `user_bans.reason_visible` and is SHOWN to the banned
  person; a reason of any older ban (or a v1 ban) is a staff-only note and is never shown. Before sign-in the app asks `check_login_access_v2(device ids, email, phone)` (callable by anon) which finds an
  ID-banned account by its email / phone, a banned phone or a blocked identity, and returns the end time and the visible reason; `AuthController.signupBlockedMessage` writes "Your account is banned until
  27 Oct 2026, 14:30." plus a second line "Reason: ...", already translated (`tr`), and the login screen keeps it as the red notice banner (no duplicate snackbar). A database without the v2 function falls back to
  `check_signup_access`. Ban ends are shown with their time (`formatBanDate`). The reason is readable by anyone who types the banned email on the login screen, so the panel tells staff to write it for the user.
